# ADR-0004：多渠道客户端与低成本验证路径

日期：2026-10-24  
状态：Accepted  
关联：`docs/product/PRD.md`、`docs/project/WBS_MILESTONES.md`、`docs/tech/ARCHITECTURE.md`

## 背景

国内应用商店正式上架通常需要企业/个体主体、软著、App 备案等前置条件；而 MVP 的核心风险不是“能不能打包”，而是“用户是否愿意录音、结果是否有用、是否愿意复测”。

同时，不同渠道的录音格式、鉴权、跨域、存储访问方式差异明显：

- Flutter：m4a/AAC
- H5：webm/opus、mp4/aac
- 微信小程序：mp3/AAC

如果不提前定义跨端边界，后续会出现“每个端一套后端逻辑”的架构腐蚀。

## 决策

1) **Go API/BFF 保持渠道无关**：App、H5、小程序共享内容 API、推理编排、发布灰度、埋点、指标。
2) **H5 先行验证**：用 H5/预约页验证需求，不注册公司；验证达标后再进入主体/资质/商店阶段。
3) **Flutter 负责商店体验**：保留现有 Flutter App；补齐 android/ios 平台工程后用于 TestFlight/内测/商店。
4) **小程序按需且与 H5 共用代码**：如必须做小程序，使用 uni-app/Taro 产出 H5+小程序；**不让 Flutter 覆盖小程序**。
5) **音频标准化是跨端前置**：所有渠道统一在服务端转 16kHz/mono/PCM WAV，推理侧只接收标准输入。
6) **公网安全前置**：H5 暴露前必须用签名 token 替换 `dev-token-*`，并补 CORS 白名单、HTTPS、限流。
7) **分享渠道化**：`share_asset` 增加 `channel`，按 App/H5/小程序返回不同模板。
8) **MVP 不做支付/订单/带货/微服务**：商业化与复杂拆分留到验证达标后。

## 备选方案

1) **直接注册公司 + 上商店**：验证慢、成本前置，失败时沉没成本高。  
2) **Flutter Web 当 H5**：可复用 Dart，但包体大、录音能力受限、无法覆盖小程序。  
3) **每端一套后端接口**：短期快，长期不可维护，直接否决。

## 后果

### 正向

- 验证阶段不需要公司，成本最低。
- 后端与内容系统只维护一套，渠道差异集中在客户端与适配层。
- H5 数据可直接与 App 对比，指导是否进入商店阶段。

### 负向

- 结果页 UI 可能在 H5 与 Flutter 各实现一次；通过统一 API 契约与设计稿降低漂移。
- 需要新增音频转码、CORS、签名 token、存储跨端配置等工作包（见 WBS 1.5/1.6/3.6/3.7/3.8）。
